技术实现方案对比（三选一）

后端语言 + 模型服务组合 + 部署策略的整体方案

A

🟢 方案 A：Python FastAPI + Ollama 全家桶（推荐 · MVP 速度优先）

后端：Python FastAPI（WebSocket 音频流 + 会话状态机）

LLM：Ollama 部署 Qwen2.5-7B / Llama3-8B（GGUF Q4_K_M 量化，约 5GB 内存）

ASR：Faster-Whisper（large-v3 量化版，约 3GB）或 Ollama 内置 Whisper

TTS：Piper TTS（轻量模型，约 100MB）或 Coqui TTS

部署：全部 Docker Compose 编排（Ollama 容器 + FastAPI 容器 + 模型文件卷挂载）

✅ 优势

  • 开发速度最快，Python AI 生态最成熟
  • Ollama 一键部署模型，省心省力
  • 调试简单，社区资源多

⚠️ 劣势

  • Python GIL 下高并发弱于 Rust
  • 内存占用略高（多个 Python 进程）
  • 16G 内存可能需要精细调参
B

🔵 方案 B：Rust Axum + llama.cpp 原生（性能优先）

后端：Rust Axum（异步 WebSocket + 无锁状态机）

LLM：llama.cpp server（Apple Silicon 原生加速，7B Q4_K_M，约 4.5GB）

ASR：whisper.cpp server（Apple Silicon 优化，约 2GB）

TTS：Piper TTS（C++ 后端，Rust 调用）或 Rust 原生 TTS crate

部署：全部原生二进制或 Docker 封装，最低内存开销

✅ 优势

  • 内存占用最小，16G 利用率最高
  • Apple Silicon 原生优化，延迟最低
  • Rust 后端并发强，稳定性高

⚠️ 劣势

  • Rust 开发周期长，迭代慢
  • AI 生态库不如 Python 丰富
  • 排错成本高，模型兼容性需验证
C

🟣 方案 C：混合架构（平衡 · 推荐长期方案）

网关：Rust Axum（负责 WebSocket、VAD、会话编排、打断逻辑）

LLM：Ollama（Docker，7B~8B 量化）—— Axum 通过 HTTP 调用

ASR：Faster-Whisper（Python 独立服务）—— Axum 通过 gRPC/HTTP 调用

TTS：Piper TTS（独立轻量服务）—— Axum 通过 HTTP 调用

部署：Docker Compose 编排 4 个微服务容器

✅ 优势

  • 各层最优：Rust 强并发 + Python 好生态
  • 服务解耦，可独立替换升级模型
  • 为未来横向扩展留空间

⚠️ 劣势

  • MVP 复杂度最高，需管 4 个服务
  • 进程间通信开销
  • 16G 内存同时跑 4 容器需测试
💡 我的推荐
MVP 阶段选方案 A（Python FastAPI + Ollama）：快速跑通闭环验证可行性，16G 内存通过 Ollama 的 offload 和量化可以跑起来。 验证通过后再迁移到方案 C（混合架构），把网关层换成 Rust 提升稳定性和并发。这样风险最低，迭代速度最快。
