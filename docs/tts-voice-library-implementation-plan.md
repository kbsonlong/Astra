# Astra 音色库实现任务清单

> 更新时间：2026-10-01
> 关联文档：[页面方案](tts-voice-library-page-plan.md) · [线框稿](tts-voice-library-wireframes.md) · [视觉规范](tts-voice-library-visual-spec.md)
> 范围：第一期“安全且可使用”的音色库与实时会话选择闭环。

## 1. 实施原则

- 一项任务只完成一个明确职责，并单独提交；
- 会议声纹档案与 TTS 音色库不互相复用数据或 UI；
- IndexTTS 在目标 Mac 完成真实模型验收前保持实验性，系统默认 Piper 路径必须持续可用；
- 所有音色合成固定引用 `voice_id + voice_revision`，不得在任务执行中读取可变的“当前音色”；
- 涉及授权、撤销、归档和试听的变更必须补充后端与前端回归测试；
- 不展示服务器绝对路径、参考文本、密钥或未经授权的音频资产。

## 2. 依赖关系

```text
TTS-00 多引擎路由决策（已完成）
       └── TTS-00A 多引擎 Router 实现
              └── TTS-01 API 缺口审计与契约
       ├── TTS-02 指定版本试听 API
       │     ├── TTS-03 后端健康/能力模型
       │     └── TTS-06 音色库前端数据层
       ├── TTS-04 IndexTTS 真机 L2/L3 验收
       │     └── TTS-09 IndexTTS 用户开放门禁
       └── TTS-05 音色库后端测试补齐

TTS-06 音色库前端数据层
       ├── TTS-07 音色库列表与详情
       ├── TTS-08 新建音色与授权向导
       └── TTS-10 实时助手音色选择

TTS-00A + TTS-03 + TTS-10 + TTS-09 → TTS-11 端到端验收与发布
```

## 3. 任务清单

### TTS-00：确定 TTS 单/多引擎运行时策略

**目标**：消除“系统默认 Piper 与 IndexTTS 音色可同时选择”的产品假设和当前单 client 实现之间的冲突。

**决策选项**：

- **单引擎 MVP（推荐）**：保持一个 `TTS_BACKEND`；实时选择器仅显示当前 backend 兼容且可用的音色；“系统默认”指当前 backend 的默认声音。
- **多引擎路由**：新增 router，管理多 client 生命周期、模型内存、队列、健康、会话快照和失败回退；只有完成这些能力后，才能在同一选择器同时显示 Piper 与 IndexTTS 音色。

**验收**：

- 决策与原因记录在产品/部署文档；
- 实时选择器、健康接口和回退文案使用同一策略；
- 不存在“显示为可选、实际无法被当前运行时合成”的音色。

**建议提交**：`docs(tts): decide session engine routing strategy`

> 决策记录：2026-10-01，采用多引擎路由。详细设计见 [多引擎 TTS 路由设计](tts-multi-engine-router-design.md)。

### TTS-00A：实现多引擎 TTS Router

**目标**：将当前单一 `TTS_BACKEND` client 改为按会话选择的 router，使默认 Piper 与 IndexTTS 音色能够在同一应用进程中共存。

**范围**：

- 新增 `TtsRouter`，实现普通合成、snapshot 合成、健康能力聚合和 `aclose()`；
- 为 Piper、IndexTTS 等 client 注册懒加载 factory，按引擎独立队列和并发上限；
- 默认会话允许使用配置的系统回退；带 `voice_id + revision` 的会话绝不静默回退；
- 在 `Session` 冻结解析后的 engine key，并扩展 health 为逐引擎结果；
- 配置 `TTS_ENABLED_BACKENDS`、默认 backend、预览队列和实时队列；
- 更新 `VoicePipeline`、应用生命周期和相关测试。

**验收**：

- Piper 默认会话与 IndexTTS 指定音色会话可在同一进程内分别完成；
- IndexTTS 不可用不会影响 Piper 会话；
- 指定 IndexTTS 音色失败时不会产生 Piper 音频；
- IndexTTS 未被选择时不加载模型；
- 应用关闭后已实例化 client 的 executor 全部关闭。

**建议提交**：`feat(tts): route synthesis across configured engines`

### TTS-01：冻结 API 契约与现状差异

**目标**：把已存在的音色库路由、数据状态和前端所需 DTO 固化为可测试契约，明确缺失能力。

**范围**：

- 盘点 `/api/tts/voices` 的列表、详情、revision、授权、激活、归档、撤销及音频下载接口；
- 定义前端统一使用的 `Voice`、`VoiceRevision`、`VoiceAvailability` 和分页 DTO；
- 明确哪些状态可显示参考音频、可试听、可用于实时会话；
- 修复并固化撤销访问规则：任意 `revision.lifecycle=revoked` 或 `consent_status=revoked` 的参考音频均不可通过下载接口读取，即使该 voice 的其他 revision 仍为 active；
- 定义 `/api/health` 中 TTS 引擎、克隆能力、模型可用性和安全原因的前端字段；
- 记录错误码与中文用户提示的映射规则。

**不包含**：实现新的 UI 或把 TTS 配置暴露到通用配置接口。

**验收**：

- API 契约写入本任务对应的测试或 OpenAPI 注释；
- 未授权、草稿、归档、撤销和 active 音色的行为矩阵明确；
- 已撤销的非当前 revision 也返回不可访问状态，不能只检查 voice 的整体状态；
- DTO 不包含绝对路径、token 或参考文本。

**建议提交**：`docs(tts): define voice-library frontend contract`

### TTS-02：实现指定 revision 的试听合成 API

**目标**：用户可对已经授权的指定音色版本生成短试听，不影响实时会话。

**范围**：

- 增加 `POST /api/tts/voices/{voice_id}/test`；
- 请求接受受限长度的 `text` 和可选明确 `revision`；
- 仅允许 `active + ready + consent confirmed` 的 revision；
- 使用音色快照调用支持 `synthesize_snapshot` 的 TTS client；
- 返回可播放 WAV，并回显安全的音色 revision、引擎和模型 revision 元数据；
- 为试听引入独立的并发/队列上限，满载时返回明确的 429；
- 不可用的后端返回可理解的 409/503，而不是延迟到超时。

**不包含**：长文本导出、批量合成或持久保存试听结果。

**验收**：

- r1 试听开始后创建 r2，不会导致 r1 请求改用 r2；
- 未确认授权、归档、撤销或不匹配后端均不能试听；
- 试听失败不阻塞实时 WebSocket 或 ASGI 事件循环；
- 测试响应可由浏览器 `<audio>` 正常播放。

**建议提交**：`feat(tts): add revision-pinned voice preview`

### TTS-03：暴露安全的 TTS 能力与可用性状态

**目标**：让页面在用户点击“试听/开始通话”之前就知道可用引擎与不可用原因。

**范围**：

- 扩展健康检查的 TTS 结果，至少提供 backend、available、reason、languages、clone、sample_rate 和 model revision；
- 将“已安装但模型目录不存在”“不支持克隆”“没有可选音色”区分开；
- 确保 reason 不泄漏真实模型路径、密钥或参考音频路径；
- 前端将健康状态映射为可用、实验性、未就绪和回退提示。

**验收**：

- Piper、MLX Audio、CosyVoice、IndexTTS 的能力字段稳定；
- 关闭或缺失 IndexTTS 时，系统默认 TTS 仍然可被选择；
- 健康接口错误可在页面上转化为操作建议。

**建议提交**：`feat(health): expose safe tts voice capabilities`

### TTS-04：完成 IndexTTS 真机 L2/L3 验收

**目标**：确认目标 Apple Silicon 设备上 IndexTTS 能稳定产出短句并重复使用同一模型/音色上下文。

**范围**：

- 准备模型目录和足够磁盘空间；
- 执行真实短句合成、同进程连续调用、不同音色 revision 切换；
- 记录首句耗时、热调用耗时、峰值内存、Metal 内存、输出采样率和失败栈；
- 验证 WebSocket 的 `tts_start`、`tts_chunk`、`tts_end`、打断和 Piper 回退；
- 按既有 IndexTTS 验收脚本保存不含敏感音频的结果摘要。

**前置条件**：目标机器有完整模型、授权测试参考音频和足够可用磁盘空间。

**验收**：

- L2 短句输出为非空、可播放的单声道 PCM16 WAV；
- L3 同一进程连续三次调用无重载、无崩溃、无明显内存持续增长；
- 打断旧 generation 后不再播放旧音频；
- 以不超过 30 个汉字的测试句为基线，单次冷启动首音不高于 15 秒；同一进程至少 20 次热调用的首音 P95 不高于 5 秒。若未达标，保持实验性而非开放给实时会话；
- 在 16 GiB 目标 Mac 上，连续三轮后须保留至少 3 GiB 系统可用内存，且不出现系统内存压力告警；
- 至少由两名评审者复听中文短句、数字/英文混读和连续三句，记录清晰度、音色一致性、异常断句和不可接受的发音错误；
- 指标和失败记录写入验收记录。

**建议提交**：`test(tts): record indextts mlx device validation`

### TTS-05：补齐音色库后端回归测试

**目标**：覆盖音色资产、状态迁移和试听边界，防止 UI 接入后放大数据/授权风险。

**范围**：

- 覆盖创建、分页搜索、元数据更新、revision、新旧版本、激活、归档、恢复和撤销；
- 覆盖 WAV 格式、时长、空文件、大小、路径穿越和失败清理；
- 覆盖 consent 状态与音频下载权限；
- 覆盖 TTS-02 试听接口、revision 固定、并发上限和后端不可用；
- 覆盖 `start_session` 的 voice snapshot 解析与错误回传。

**验收**：

- 所有状态转换都有正反例；
- 参考资产不越过音色库目录；
- 撤销授权后不得发起新的试听或会话选择；
- 既有 TTS、会议和 WebSocket 测试继续通过。

**建议提交**：`test(tts): cover voice library lifecycle and previews`

### TTS-06：建立前端音色 API client 与状态模型

**目标**：将音色请求、错误、分页与试听状态从页面组件中抽离，避免再形成单一巨型页面。

**状态**：已实现领域模块与单元测试，待依赖齐备后运行完整前端测试套件。

**范围**：

- 新建 `frontend/src/tts/` 领域模块；
- 集中定义 API DTO、请求方法、错误转换和状态判断函数；
- 定义 `canPreview`、`canUseInSession`、`availabilityLabel` 等纯函数；
- 支持请求取消与重复试听防抖；
- 为前端数据层添加单元测试。

**不包含**：具体页面布局或 WebSocket 会话参数变更。

**验收**：

- 页面不直接散落拼接 TTS API URL；
- 后端 401、409、422、429、503 在 UI 层有一致的用户文案；
- 请求被取消时不把旧试听结果写入新选择的音色。

**建议提交**：`refactor(frontend): add tts voice api client`

### TTS-07：实现音色库列表与详情页

**目标**：用户可发现、筛选和理解已有音色及其状态。

**状态**：已实现列表、筛选、详情、版本历史、参考音频播放与只读状态展示；创建、授权和试听写操作留待 TTS-08。

**范围**：

- 添加导航项、路由和 `VoiceLibraryPage`；
- 实现搜索、状态/引擎筛选、分页、空状态和模型未就绪提示；
- 实现音色卡片、参考音频播放器、状态徽章和详情视图；
- 展示当前 revision、版本历史、授权摘要和安全元数据；
- 严格按视觉规范适配浅色、深色和窄屏。

**不包含**：创建、授权、试听、激活或归档写操作。

**验收**：

- 草稿、可用、归档、撤销、引擎不可用五种状态可清楚区分；
- 列表和详情不会泄漏绝对路径或未授权资源；
- 音频控件可键盘操作并具备可读标签；
- 页面在 1080px 以下仍能完成筛选和查看详情。

**建议提交**：`feat(frontend): add tts voice library browser`

### TTS-08：实现新建音色、授权与版本向导

**目标**：用户无需 API 工具即可安全入库和激活音色。

**状态**：已实现四步创建/新版本向导、授权确认、指定版本试听、启用与高风险操作确认。

**范围**：

- 实现基本信息、上传参考音频、授权确认、试听与启用四步流程；
- 上传前明确 WAV、5–15 秒、单人、安静环境等要求；
- 把后端格式/时长/大小错误映射为可执行的修复建议；
- 实现显式授权确认与备注；
- 实现激活、创建新 revision、归档、恢复和撤销授权的确认交互；
- 危险操作采用二次确认，不提供默认硬删除。

**依赖**：TTS-02、TTS-06、TTS-07。

**产品规则**：试听是推荐的合成预检，不是激活的硬性前置条件。模型未就绪时允许管理员完成入库、授权和激活，但页面必须区分“已启用”与“当前可用于合成”。

**验收**：

- 用户可完成“上传 → 授权 → 试听 → 激活”而不离开产品；
- 失败时保留用户已输入的名称、备注和试听文本；
- 新 revision 不覆盖旧版本；
- 撤销授权后音色立刻不可用于新的试听和会话。

**建议提交**：`feat(frontend): add voice creation and consent flow`

### TTS-09：增加 IndexTTS 用户开放门禁

**目标**：在真实模型未验证或不稳定时，不将 IndexTTS 误呈现为可用生产能力。

**状态**：已增加 `TTS_INDEXTTS_VALIDATED` 门禁；健康能力会区分技术可用与已通过设备验证，未验证时禁止用户侧试听与会话选择。

**范围**：

- 定义显式能力门禁，例如 `tts.indextts.validated`；
- 未通过 TTS-04 时，音色库显示为“实验性 / 未完成设备验证”；
- 未满足门禁时禁用 IndexTTS 试听和实时选择，并显示系统默认 TTS 回退；
- 仅允许管理员通过明确配置启用实验能力；
- 在健康结果、音色库和实时助手中使用同一门禁状态。

**验收**：

- 仅配置了模型路径不等于“用户可用”；
- 未验证或不可用时无法误选 IndexTTS 音色；
- Piper 默认路径与既有实时功能不受影响。

**建议提交**：`feat(tts): gate indextts behind device validation`

### TTS-10：实现实时助手音色选择与会话快照

**目标**：用户在通话前选择已授权、兼容的音色，整场会话固定使用该 revision。

**状态**：已实现可用音色选择、音色库预选、`start_session` 快照字段、会话锁定与撤销/不可用状态提示。

**范围**：

- 在实时助手“开始通话”前增加回复音色选择器；
- 仅列出 `active + consent confirmed + backend compatible + available` 音色；
- 系统默认 TTS 始终作为第一个稳定回退选项；
- `start_session` 传递 `voice_id` 与 `voice_revision`；
- 通话开始后锁定选择器，显示当前引擎、音色名称和 revision；
- 处理 snapshot 不可用、模型不可用、会话重连和授权撤销后的用户提示；
- 从音色库“用于本次会话”跳转时允许预选，但不自动开启麦克风。

**依赖**：TTS-00A、TTS-03、TTS-06、TTS-07；IndexTTS 项依赖 TTS-09。

**验收**：

- 前端会话消息与选择项一致；
- 会话期间音色版本不会因创建新 revision 而变化；
- 重连不误用旧连接的音色/生成事件；
- 用户可在失败前切换至系统默认音色；
- 无可用克隆音色时，实时助手仍能用 Piper 对话。

**建议提交**：`feat(live): select revision-pinned tts voices`

### TTS-11：端到端验收、可访问性与发布说明

**目标**：验证从音色创建到真实会话播放的完整体验，并更新运行文档。

**状态**：代码级验证已完成（后端 211 passed、前端 11 passed、生产构建通过）；发布说明与真机验收清单已更新。IndexTTS 目标 Mac L2/L3 验收仍为显式发布门禁，尚未在本次代码验证中执行。

**范围**：

- 补充浏览器端到端测试：创建草稿、确认授权、试听、激活、预选、会话快照、撤销；
- 测试键盘导航、焦点、`aria-live`、深浅主题和窄屏布局；
- 在真实 Mac 上验证首句/热调用延迟、打断、TTS 与 ASR/LLM 并行负载；
- 更新用户指引、部署文档、验收清单和配置示例；
- 明确 IndexTTS 的实验性状态、磁盘/模型要求和 Piper 回退行为。

**依赖**：TTS-02 至 TTS-10。

**验收**：

- 关键主链路在浏览器中可重复完成；
- 自动化测试、前端构建和受影响的后端测试通过；
- 真实设备验收与自动化测试结果分开记录；
- 用户文档不将未验证 IndexTTS 表述为默认可用能力。

**建议提交**：`test(e2e): validate tts voice library workflow`

## 4. 推荐实施顺序

1. TTS-00 已完成；先实现 TTS-00A，避免 UI 假设多引擎回退而运行时只有单 client；
2. 再完成 TTS-01，避免页面依赖不稳定或含糊的接口字段；
3. TTS-02、TTS-03、TTS-05 可先后或并行推进，构成可被前端安全消费的后端基础；
4. TTS-06 后开始 TTS-07，再完成 TTS-08；
5. TTS-04 与前端管理页可并行，但 TTS-09 是 IndexTTS 面向用户开放前的硬门禁；
6. 完成 TTS-10 后，由 TTS-11 统一做端到端、设备和文档验收。

若目标是尽快交付非克隆 TTS 的音色管理，可先用系统默认 TTS 完成 TTS-01 至 TTS-08 与 TTS-11 的管理路径；IndexTTS 试听和会话选择则保留在 TTS-04/TTS-09 门禁之后。
