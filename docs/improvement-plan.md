# Astra 分阶段改进计划

> 制定日期：2026-10-04
> 
> 依据：对当前后端、前端、任务持久化、部署配置和现有测试的代码审查。

## 目标与现状

Astra 已经具备 FastAPI、React、独立会议任务、SQLite 任务登记、WebSocket 实时会话、上传限制和较完整的单元测试。当前最需要解决的是长任务生命周期和跨层状态一致性：部分问题在服务连续运行、生产 Nginx 或浏览器断线后才会出现，现有单元测试尚未覆盖这些场景。

当前基线：后端 pytest 212 项通过，前端 Vitest 11 项通过，前端生产构建通过。静态检查和真实 Mac mini、模型、麦克风、远端 LLM 验收需要单独执行。

## 执行原则

- 每个阶段单独提交并通过验收，再进入下一阶段。
- 先修复可复现的正确性问题，再做结构性重构。
- 任务状态以持久化记录为准，浏览器连接只负责展示和订阅。
- 会议处理继续保留时间戳、说话人和可用的降级结果。
- 不在同一个变更中混合模型质量调参和任务生命周期重构。

## 阶段一：修复直接影响使用的缺陷

### 目标

保证会议可以连续提交，生产部署可以订阅状态，实时连接断开时能够释放资源，审校不会静默覆盖其他人的修改。

### 工作项

1. 会议子进程完成或失败时，可靠同步 `TaskStore` 终态并释放并发名额；不能依赖浏览器打开状态订阅来触发同步。
2. 为 Nginx 下的 `/api/meeting/*/events` 和 `/api/notifications/events` 配置 WebSocket 升级头、长连接超时和必要的代理设置。
3. 将实时会话的任务取消、录音结束和并发名额释放统一放入 `finally`；处理重复 `speech_end` 和正常断开路径。
4. 审校前端保存并提交当前 `version`；后端要求版本参与更新；发生 409 时保留用户草稿并提示冲突。
5. 补充连续会议、Nginx WebSocket、正常断开取消、审校冲突的回归测试。

### 验收标准

- 并发上限设为 1 时，会议完成后可以立即提交下一个任务。
- 通过 Nginx 可以连接实时会话、会议状态和通知三个 WebSocket。
- 浏览器断开后，生成任务和 IP 并发额度最终释放。
- 两个标签页编辑同一分段时，旧版本提交返回 409，不覆盖新内容。

### 依赖与风险

取消异步任务不一定能立即停止已经进入原生模型库的同步推理；需要分别验证“API 任务已取消”和“底层推理进程已退出”。

## 阶段二：统一长任务生命周期

### 目标

在关闭页面、API 重启、任务超时和取消的情况下，会议与训练状态仍然可靠，资源不会长期占用。

### 工作项

1. 为会议和训练建立统一任务监督逻辑，周期检查子进程退出、超时和异常状态。
2. 明确定义状态转换：`processing`、`stopping`、`done`、`failed`、`stopped`；终态不能被迟到回调覆盖。
3. 取消流程采用“发送终止信号 → 等待退出 → 必要时强制终止 → 确认退出 → 释放名额”。
4. 记录并验证进程身份，避免仅凭 PID 恢复或终止时误判 PID 复用。
5. 训练任务保存可恢复的完成结果，使 API 重启后也能判断成功或失败。
6. 明确单 API worker 的部署边界；若未来启用多 worker，再引入跨进程监督协调。

### 验收标准

- 没有浏览器连接时，超时任务仍会被处理。
- API 重启后，运行中、已完成和异常退出的任务都能正确恢复。
- 取消与自然完成同时发生时，最终状态唯一且一致。
- 进程退出确认前，不释放任务并发名额。

## 阶段三：完善结果恢复与资源治理

### 目标

网络抖动或页面刷新不丢任务入口，服务长期运行时磁盘和临时资源可控。

### 工作项

1. 明确 SQLite 任务记录和文件产物的职责；状态文件改为临时文件写入后原子替换。
2. 增加会议 HTTP 状态查询；前端支持退避重连、刷新恢复和查询兜底。
3. 区分“订阅中断”和“任务失败”，避免网络问题误报为处理失败。
4. 定时清理会议产物、实时录音和遗留临时文件，同时保护活跃任务。
5. 为音频探测和解码设置超时、临时空间预算，并明确不可解码文件的错误策略。
6. 检查请求接收阶段的上传限制和流式响应的代理缓冲设置。

### 验收标准

- 处理中断网或刷新页面后，可以重新跟踪原任务，不需要重复上传。
- 并发读写状态文件不会产生 JSON 解析错误。
- 服务持续运行时过期文件会自动清理，活跃任务不受影响。
- 无效或解码超时的音频返回明确错误，临时文件被回收。

## 阶段四：收敛代码结构与接口

### 目标

降低后续修改成本，减少前后端字段、状态和错误处理不一致。

### 工作项

1. 从 `App.tsx` 和 `UploadPage.tsx` 提取实时连接、音频采集播放、会议任务订阅等 hooks。
2. 将会议、提示词和声纹管理拆成职责清晰的前端组件。
3. 提取后端任务服务和产物访问层，让路由只处理协议转换、校验和响应。
4. 统一任务状态、审校版本和错误响应的接口类型，减少散落的手写结构。
5. 将 Mypy 覆盖逐步扩展到任务服务、路由边界和模型协议。
6. 整理 SQLite 初始化和连接生命周期，避免每次请求重复承担初始化职责。

### 验收标准

- 既有 API 和用户流程行为保持不变。
- 连接和任务生命周期可以脱离页面单独测试。
- 接口字段遗漏能由类型检查或契约测试发现。
- 阶段一至三的回归测试全部通过。

## 阶段五：发布和模型验收

### 目标

让构建、部署和模型变更都能重复验证，并量化真实设备上的质量和资源开销。

### 工作项

1. Docker 构建复制 `package-lock.json` 并使用 `npm ci`，统一 CI 与镜像的 Node 版本。
2. 增加经过 Nginx 的集成测试和关键浏览器流程测试。
3. 基于固定录音集记录字错率、说话人效果、处理耗时和峰值内存。
4. 在真实 Mac mini 上分别验证 ASR、TTS、长会议、远端 LLM 中断和恢复。
5. 补齐任务日志关联、阶段耗时、队列深度、失败原因和清理记录。

### 验收标准

- 相同提交和锁文件能够重复构建。
- 登录、会议处理、断线恢复、审校冲突等关键流程自动验证。
- 模型或推理参数变更有可比较的基线和阈值。
- 发布记录明确区分单元测试、部署集成测试和真实设备验收。

## 建议的提交顺序

1. 阶段一：任务终态、WebSocket 代理、连接清理、审校版本。
2. 阶段一补充：为上述问题增加跨层回归测试，并提前修复 Docker 的锁文件安装方式。
3. 阶段二：统一任务监督、取消和重启恢复。
4. 阶段三：原子产物、断线恢复和持续清理。
5. 阶段四：前后端职责拆分和类型收敛。
6. 阶段五：部署门禁、模型基线和真实设备验收。

模型质量基线可以在阶段一之后提前建立，但完整发布门禁放在阶段五收口。

## 每阶段通用验证

后端变更至少执行：

```bash
PYTHONPATH=backend .venv/bin/pytest -q backend/tests
```

前端变更再执行：

```bash
cd frontend
npm test
npm run build
```

涉及任务生命周期或部署时，还需要执行对应的跨层测试和真实设备验收；单元测试通过不能替代这些验证。
